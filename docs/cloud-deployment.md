# Cloud deployment

This system is deployable on any major cloud with the same three moving pieces
(see `infra/README.md` for the Terraform): a managed Postgres warehouse, the
dashboard as a small container service, and the ETL pipeline as a scheduled job.
Nothing here has been applied against a live account — this documents the pattern
`data-platform-engineer` would follow, and the IaC under `infra/` is illustrative.

## The only thing that actually changes: `DATABASE_URL`

`connectors/warehouse.py` reads `DATABASE_URL` and falls back to the local SQLite
sample warehouse if it's unset. Every agent, skill, pipeline, and the dashboard goes
through this one connector — so moving from the local sample warehouse to a managed
cloud database is a config change, not a code change:

```bash
# AWS RDS
DATABASE_URL=postgresql+psycopg2://analyst_app:<password>@<rds-endpoint>:5432/analytics
# GCP Cloud SQL (via the Cloud SQL Auth Proxy, or a private IP connection)
DATABASE_URL=postgresql+psycopg2://analyst_app:<password>@/analytics?host=/cloudsql/<connection-name>
# Azure Database for PostgreSQL
DATABASE_URL=postgresql+psycopg2://analyst_app:<password>@<server>.postgres.database.azure.com:5432/analytics
```

In all three cases the connection string is generated by Terraform and stored in
the cloud's secret manager (Secrets Manager / Secret Manager / Key Vault) rather
than committed anywhere — see each `infra/<provider>/main.tf`.

## Provider comparison

| Concern | AWS | GCP | Azure |
|---|---|---|---|
| Warehouse | RDS for PostgreSQL | Cloud SQL for PostgreSQL | Azure Database for PostgreSQL (Flexible Server) |
| Dashboard hosting | ECS Fargate service | Cloud Run service | Container Apps |
| Scheduled ETL | EventBridge Scheduler → one-off ECS task | Cloud Scheduler → Cloud Run Job | Container Apps Job (cron trigger) |
| Secrets | Secrets Manager | Secret Manager | Key Vault |
| Best fit when... | already on AWS, or want the most mature ecosystem | want the simplest serverless container story (Cloud Run's per-request billing) | already on Azure / Microsoft-centric org |

None of these is "correct" in the abstract — pick based on where the rest of the
company's infrastructure already lives. Cross-cloud portability is exactly why the
connector abstraction exists: the agents and pipeline code never need to know
which one you picked.

## What's deliberately not deployed

The agents themselves (`.claude/agents/`) run inside Claude Code as a development
and analysis tool — they are not a backend service with its own deployment. What
*is* deployable and shown here is the data infrastructure they depend on (the
warehouse) and the artifacts they produce for stakeholders (the dashboard). A
"hosted agent API" is a reasonable future direction but is out of scope here —
see `docs/ARCHITECTURE.md` for how agent orchestration would need to change if
that were built.

## Production checklist before pointing at a real warehouse

- [ ] Database user is read-only / least-privilege (see `docs/ARCHITECTURE.md`
      security section) — never point `DATABASE_URL` at a role with write access.
- [ ] Secrets come from the cloud secret manager, never a committed `.env`.
- [ ] `pipelines/data_quality.py` checks are wired into the scheduled ETL job's
      exit code, so a failed check fails the job instead of silently loading bad
      data.
- [ ] `ml/check_drift.py` runs on a schedule (e.g., alongside the ETL job) if a
      model is in production use, not just on demand.
